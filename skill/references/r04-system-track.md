# r04 系统先行分支:先把系统做出来,再照着真系统写论文

对应流水线步骤 4,**仅当需求单标记"系统先行"时执行**;纯写作项目跳过本步并在执行记录注明。

适用:论文要求交付真实可运行的软件/系统(计算机毕设/课设:管理系统、平台、小程序、算法演示系统),论文的系统设计、实现、测试章节必须基于真跑过的系统。

分两个子阶段:**规划**(先把边界定死,§1)→ **一口气开发交付**(真做出来,§2)。本文件是两个子阶段的完整执行规范。

## 〇、判定与产出

| 项 | 内容 |
|---|---|
| 触发 | 需求单标记"系统先行"(任务书要求交系统,或用户在问询中确认) |

## 一、规划子阶段(定边界)

核心原则:**最小可行开发优先、交付效率优先、边界清晰优先**。

必须落到《系统需求与技术方案.md》+《开发执行计划.md》的硬约束:
1. **范围**:一期必做 / 可延后 / 明确不做;为什么这个边界"最小可行且可交付";不为"看起来完整"加功能;
2. **开源借鉴决策**:显式做 adopt / reject / fallback 判断(交付速度、改造成本、UI 自由度、许可证、与最小范围匹配度);
3. **部署**:未要求 Docker 则默认轻量本地方案;必须规划一键启动/停止/重置灌数/导出;
4. **数据生命周期**:演示/测试数据从哪来、如何灌入重置(幂等)、导出物放哪、哪些数据用于论文;
5. **API 与字段契约**:核心字段、必填/可空/默认值、状态流转、空值异常处理;
6. **UI/UX 基线**(有界面必做):关键页面与交互、溢出/遮挡/拥挤预防、空态/加载/异常/成功反馈、表单校验提示可理解性——不许只写"界面简洁美观";
7. **验收链路**:每个核心角色一条完整路径,至少一条跨角色闭环;"怎么操作/预期结果/沉淀什么证据";
8. **停止条件**:测试、回归、截图沉淀与"何时才能停止开发"写进执行计划;
9. **文案边界**:系统前台只放面向最终用户的文案,开源借鉴说明/论文写作说明/内部实现说明严禁进前台。

缺失信息不编造,标注 `待确认` 并写明影响。

## 二、开发交付子阶段(做出来)

- 严格以两份规划文档为基线开发,不脱离扩展;与规划不一致时**回写规划文档**并标注修订;
- 在 `work/` 下建独立交付目录,不污染项目根目录;
- 顺序:先可运行骨架与数据生命周期(启动/停止/重置/灌数/导出脚本)→ 打通最小跨角色闭环 → 补角色内功能 → 补空态/异常/边界;**不许先堆模块最后串闭环**;
- 有前端时同步处理用户可见质量(信息优先级、文案边界、布局、错误提示),页面检查不能只做接口冒烟。

### 必须防住的真实坑
1. 脚本退出码 0 ≠ 服务可用:必须验证真实端口、健康检查、页面入口;
2. 接口能跑 ≠ 页面能交付:查文本溢出、按钮遮挡、异常提示可理解性、无系统外文案污染;
3. 重置/灌数是正式交付能力:验证可重复执行、幂等,第二次执行不得报脏数据;
4. 可空字段与异常路径实测:不向前台暴露 null/堆栈/原始报错;
5. 文档与真实系统一致:README/部署说明/用户手册中的命令、路径、账号、地址全部实测。

### 交付文档(必须齐)
README 总入口、部署说明(小白可操作)、用户手册、`docs/测试报告.md`、`docs/generated/regression-summary.md`、截图清单。

## 三、守门与停止条件

放行标准(全部满足才能进入论文大纲步骤):
- P0 功能全部可用,关键闭环真实跑通;
- 自动化测试/接口或页面冒烟/关键链路回归通过;
- 一键脚本(启动/停止/重置/导出)真实可执行;
- 截图与导出数据已沉淀到 `output/work/data/` 与截图清单。

环境反复跑不通、依赖无法安装 → **停止,问人**:说明卡点、已尝试方案,请用户决定(换技术栈/降低范围/提供环境)。
